A curation write that adds or changes state (a note, a non-empty tag or split set, a category) whose transaction id names no transaction at all — not the id itself, and nothing it forwards to — is now refused with a `transaction_reference_not_found` error instead of being silently accepted. This resolution now covers every curation writer, including the `transactions_annotate` MCP tool (notes, tags, and splits submitted as a batch) and the guarded categorization write behind `transactions_categorize_commit` and the rule/merchant/Plaid engine passes — previously only the granular per-field writers carried this check.

A curation write that only removes state — removing tags, clearing splits, clearing a category, or setting an empty tag or split list — never refuses for liveness: it resolves a superseded id to its live transaction when one exists, and otherwise stays the idempotent no-op it always was. Refusing a removal on a dead id would block cleanup of curation stranded on an id no automatic healing pass can reach.
